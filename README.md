# Dray

Dray deploys code from Git to its targets — Kubernetes through GitOps, Piral
feeds, and more — for people and for AI agents, without either holding cloud
credentials. Every deploy is a plan, then an apply, pinned to one commit;
production waits for a person's passkey.

This branch is Dray v2, a new build in Go. It replaces the JS `dray` CLI
(`@brutalsystems/dray`, on `main`) once it reaches parity.

**Status:** milestone M0.5, the CLI deploy. `dray config migrate` converts a
JS-tool `.dray/config.json`, `dray config validate` checks the result, and
`dray config schema` prints the JSON Schema. `dray render` prints a repo's
manifests with image references filled in, byte for byte as the JS tool
rendered them. `dray secrets import` copies a repo's sops and env-file secrets
into the configured store (OpenBao or a folder of files). `dray deploy` (alias
`ship`) builds, pushes, applies and rolls out a repo's workloads; `--dry-run`
shows what would change.

## Build

Requires Go 1.26 (pinned in `.tool-versions`).

```bash
make build      # bin/dray, bin/dray-server
make test       # go vet + go test -race
make lint       # golangci-lint
make snapshot   # goreleaser: every platform into dist/
```

| `internal/server` | Deploy on merge: GitHub webhooks, the CI check, one deploy per repo at a time, results as check runs |

| `internal/pilet` | Building, packing, versioning and uploading pilets |

| `internal/version` | Version info, set at release time |
| `docs/decisions.md` | Why Dray is built the way it is |

## A repo's `.dray/` folder

Everything Dray needs to build and deploy an app is in its repo, in
`.dray/config.yaml`: the images, the workloads, where the app deploys, and
where its secrets live. Anyone who clones the repo, has Dray installed and has
the access (cloud, cluster, secret store) can deploy it.

```yaml
name: shop
images:
  - name: api
workloads:
  - name: api
    kind: deployment
    images: [api]
    manifests: [k8s/api.yaml]
    secrets: [api-secrets]
secrets:
  - name: api-secrets
    from: secret:shop/api-secrets
environments:
  prod:
    target: cluster-a
    namespace: shop
    release: direct
    approval: none
targets:
  cluster-a:
    cloud: aws
    account: "123456789012"
    region: us-east-2
    cluster: cluster-a
    platform: linux/arm64
secret_store:
  type: openbao
  openbao:
    address: https://bao.example.com
    mount: kv
    layout: "{client}/{app}/{env}/{name}"
    client: acme
```

Credentials are never in it. Your own settings, `~/.config/dray/config.yaml`
(optional), hold only what differs per person:

```yaml
aws_profiles:
  "123456789012": my-deploy-profile    # default: the AWS CLI's usual credentials
kube_contexts:
  cluster-a: my-context                # default: the cluster's name
```

Since the repo says where the app deploys, protect it: changes to `.dray/`
should need the owner's review (CODEOWNERS), and Dray only ever reads where
an app may deploy from the main branch. Dray labels each namespace it creates
with its app (`dray/app`) and refuses to deploy another app into it.

### Secret store

Repos refer to secrets as `secret:<app>/<name>`. With the layout above,
`secret:shop/api-secrets` deployed to prod is `kv/acme/shop/prod/api-secrets`.
The default layout is `{app}/{name}`. The token comes from `BAO_TOKEN`,
`VAULT_TOKEN` or `~/.vault-token`, never a file. To use another store, write
an adapter that implements `secrets.Store` and passes `storetest.Run`.

## Deploying from the CLI

```bash
dray deploy --dry-run          # what each workload would change; nothing built or applied
dray deploy                    # build, push, apply, roll out (the app's only environment)
dray deploy --env dev --workload api
```

Images are built from the commit, exported into a fresh folder with any build
sources beside it (never the working tree), and referenced by digest. An image
the registry already holds for the commit is reused. A rollout is undone only
when Kubernetes reports it failed.

## Publishing pilets

`dray publish` builds a repo's pilets, packs them with the pilet CLI and
uploads them to the feed of a `release: feed` environment:

```yaml
pilets:
  names: [cart, checkout]
  path: packages/pilet-{name}          # default packages/{name}
  build: [yarn, build:pilet]           # run in the pilet's folder; default npx pilet build
environments:
  dev:
    release: feed
    approval: none
    feed:
      url: https://feed.example.com/api/pilet/publish/shop-dev
      api_key: secret:shop/feed#FEED_API_KEY
      version: commit                  # default: 1.2.0 becomes 1.2.0-dev.<commit>; or package
```

```bash
dray publish --dry-run --pilet cart    # build and pack only
dray publish --env dev
```

## Deploy on merge

`dray-server serve` deploys an app when CI passes on its main branch. It is a
GitHub App: on each `workflow_run` webhook for a push to the default branch,
once every CI run for that commit has passed, it downloads the commit, finds
each `.dray/config.yaml` in it (an app at the root or in subfolders), and
deploys every environment with `on_merge: deploy` using the same code as
`dray deploy`. Each result is a check run on the commit. One commit per repo
deploys at a time; merges that arrive meanwhile collapse into the latest.

Builds run in a BuildKit pod started for the deploy and deleted after it, on
build-only nodes that the autoscaler adds and removes as needed
(`deploy/kubernetes/builds.yaml`, D23).

The GitHub App needs: contents read, actions read, checks write, metadata
read, the `workflow_run` event, and to be private. Create it however you
manage GitHub Apps (GitHub's manifest flow makes it one click), store its ID,
private key and webhook secret in your secret store, and install it only on
the repos Dray deploys.

A GitHub App private to an organization can only be installed there, so a
server that deploys repos of several organizations has one App per
organization, all sending to the same address. Each webhook is checked with
the secret of the App that sent it.

The server reads its Apps from the vault, signing in with its Kubernetes
service account (`DRAY_VAULT_ROLE`; each App's path in `DRAY_GITHUB_APPS`
holds `app_id`, `private_key` and `webhook_secret`), or one App from files
(`DRAY_GITHUB_APP_ID`, `DRAY_GITHUB_APP_KEY_FILE`, `DRAY_WEBHOOK_SECRET_FILE`).
Each deploy reads its app's secrets as that app's own vault role
(`DRAY_VAULT_APP_ROLE`, default `kv-{client}-{app}-{env}`), so it can read
nothing else. Builds: `DRAY_BUILD_MEMORY` and `DRAY_BUILD_CPU` (default 6Gi,
2). AWS and Kubernetes use the pod's own identity.
