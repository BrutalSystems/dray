# Dray

Dray deploys code from Git to its targets — Kubernetes through GitOps, Piral
feeds, and more — for people and for AI agents, without either holding cloud
credentials. Every deploy is a plan, then an apply, pinned to one commit;
production waits for a person's passkey.

This branch is Dray v2, a new build in Go. It replaces the JS `dray` CLI
(`@brutalsystems/dray`, on `main`) once it reaches parity.

**Status:** milestone M0.5, the CLI deploy. `dray config migrate` converts a
JS-tool `.dray/config.json`, `dray config validate` checks the result, and
`dray config schema` prints the JSON Schema. `dray render` prints a repo's
manifests with image references filled in, byte for byte as the JS tool
rendered them. `dray secrets import` copies a repo's sops and env-file secrets
into the configured store (OpenBao or a folder of files). `dray deploy` (alias
`ship`) builds, pushes, applies and rolls out a repo's workloads; `--dry-run`
shows what would change.

## Build

Requires Go 1.26 (pinned in `.tool-versions`).

```bash
make build      # bin/dray, bin/dray-server
make test       # go vet + go test -race
make lint       # golangci-lint
make snapshot   # goreleaser: every platform into dist/
```

## Layout

| Path | What |
| --- | --- |
| `cmd/dray` | The CLI |
| `cmd/dray-server` | The server (MCP, HTTP API, approvals), from milestone M1.2 |
| `internal/cli` | Command tree shared by both binaries |
| `internal/config` | `.dray/config.yaml` and registry entries: types, strict parsing, validation |
| `internal/config/legacy` | Reading and converting the JS tool's `.dray/config.json` |
| `internal/secrets` | The `Store` interface; adapters in `file/`, `openbao/`, `sops/` (read-only); `storetest/` is the conformance suite every adapter passes |
| `internal/render` | Filling image placeholders in a workload's manifests; parity test against the JS tool |
| `internal/deploy` | The deploy: plan, build, apply, roll out, with the JS tool's safety rules as tests; adapters in `docker/`, `ecr/`, `kubectl/`, `gitsrc/`, `ghci/` |
| `internal/execx` | Running external programs without a shell |
| `schema/` | Published JSON Schemas, generated by `internal/config`'s tests |
| `internal/version` | Version info, set at release time |
| `docs/decisions.md` | Why Dray is built the way it is |

## Secret store

Repos refer to secrets as `secret:<app>/<name>`; which store holds them is a
deployment setting in `~/.config/dray/config.yaml` (or `$DRAY_CONFIG`):

```yaml
secret_store:
  type: openbao            # or file
  openbao:
    address: https://bao.example.com   # default: BAO_ADDR, then VAULT_ADDR
    mount: kv                          # a KV version 2 engine
    layout: "{client}/{app}/{env}/{name}"
    clients:
      shop: acme
```

The layout follows the vault's own naming: with the one above,
`secret:shop/app` deployed to prod is `kv/acme/shop/prod/app`. The default
layout is `{app}/{name}`; `--env` names the environment.

The token comes from `BAO_TOKEN`, `VAULT_TOKEN` or `~/.vault-token`, never the
file. To use another store, write an adapter that implements
`secrets.Store` and passes `storetest.Run`.

## Deploying from the CLI

`dray deploy` reads the app's registry entry and its target from a registry
folder (`registry:` in the config file, default `~/.config/dray/registry`):

```text
registry/
  shop.yaml            # the app's environments (dray config migrate prints a draft)
  targets/
    cluster-a.yaml     # cloud account, region, kube context, build platform
```

```bash
dray deploy --dry-run          # what each workload would change; nothing built or applied
dray deploy                    # build, push, apply, roll out (the app's only environment)
dray deploy --env dev --workload api
```

Images are built from the commit, exported into a fresh folder with any build
sources beside it (never the working tree), and referenced by digest. An image
the registry already holds for the commit is reused. A rollout is undone only
when Kubernetes reports it failed.
